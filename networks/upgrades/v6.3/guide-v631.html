Why 6.3.0 will not start

v6.1 created the b3-* trees at height 23191300. v6.2 stopped mounting them and left the bytes in data/application.db. 6.3.0 marks those names as new stores at 23893261, and IAVL refuses a tree that already has an earlier version:

initial version set to 23893261, but found earlier version 23191300

6.3.1 deletes only s/k:b3-* prefixes that are absent from the latest commit, then runs the same copy onto empty BLAKE3 trees. A statesync snapshot does not contain those orphan bytes. An archive snapshot, and any node that actually ran v6.1, does.

Replace the binary and start

Stop the node first. Do not start a second process on the same home.

export DAEMON_HOME="${DAEMON_HOME:-$HOME/.terpd}"
# systemd: systemctl stop terpd
# raw process: kill the terpd whose --home is $DAEMON_HOME

curl -fL -o terpd-6.3.1-linux-amd64.tar.gz \
  https://s3.terp.network/releases/terp-core/v6.3.1/terpd-6.3.1-linux-amd64.tar.gz
# sha256sum -c against the table above before installing

install -d -m 0755 "$DAEMON_HOME/cosmovisor/upgrades/v6.3/bin" \
  "$DAEMON_HOME/cosmovisor/upgrades/v6.4/bin"
tar -xOzf terpd-6.3.1-linux-amd64.tar.gz terpd \
  > "$DAEMON_HOME/cosmovisor/upgrades/v6.3/bin/terpd"
chmod 0755 "$DAEMON_HOME/cosmovisor/upgrades/v6.3/bin/terpd"
"$DAEMON_HOME/cosmovisor/upgrades/v6.3/bin/terpd" version

Confirm upgrades/v6.4/bin/terpd version still prints 6.4.0. If that file is missing, place the published 6.4.0 tarball (33e11632d368e455ab9a906fe161445a77f7127415ebb6cc80bad2d2e05e3196 for linux/amd64) before the chain moves past 23893263. 6.3.1 arms that plan. It does not contain the 6.4.0 binary.

Start the same way you halted. Cosmovisor:

DAEMON_NAME=terpd \
DAEMON_HOME="$DAEMON_HOME" \
DAEMON_RESTART_AFTER_UPGRADE=true \
DAEMON_ALLOW_DOWNLOAD_BINARIES=false \
UNSAFE_SKIP_BACKUP=true \
cosmovisor run start --home "$DAEMON_HOME"

Without Cosmovisor, run the 6.3.1 binary itself. The plan directory is only a path Cosmovisor reads. A raw start uses the ELF you installed:

"$DAEMON_HOME/cosmovisor/upgrades/v6.3/bin/terpd" start --home "$DAEMON_HOME"

The first start deletes the orphan trees and copies every migratable store. On a full archive that can take a long time before the next block. Leave it running. A statesync home does not need the delete, and it is not a rehearsal of this failure.

What good looks like

  • Log lines v6.3: dropped orphan dest store for each b3-* name that still had v6.1 bytes.
  • Then v6.3: running module migrations and one v6.3: synced dest per migratable store.
  • terpd status moves past height 23893261. App version is 6.3.1.
  • Two blocks later the log says UPGRADE "v6.4" NEEDED at 23893263. Cosmovisor swaps to the 6.4.0 binary already on disk. A raw 6.3.1 process stops there until you start 6.4.0.
